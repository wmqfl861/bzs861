# 持久批读的共享请求与取消

本文描述持久 `read_many` 通道。后续普通 `web.read` 的独立进程内协调见[直接共享读取](DIRECT_SHARED_READS.md)；两条通道保留各自的超时、预算、取消和恢复合同，不交叉加入。schema15 批读基线已发布为 `346048b4`，其历史发布与验证见[GitHub 交付记录](GITHUB_HANDOFF.md)。

当前 schema15 在原合并派发基础上，允许兼容的新 `read_many.submit` 任务首项加入已经派发、尚未结算的持久读取尝试。本增量推进 `CACHE-01 / B-24 / FT-032`，范围仍限定为持久静态网页批读；普通 `web.read`、map/crawl、来源搜索以及不同 owner 不进入这条合并通道。现有 HTTP、CLI、MCP 批读和任务控制接口保持一致，业务仍由 C++ 核心执行。

## 合并范围

每次物理尝试最多累计 32 个成员，包含原付款任务。已经取消、暂停或失去发布资格的成员仍占用原槽位，不回收槽位接纳更多任务。匹配必须同时满足：

- owner、主体权限代际、任务创建时的删除序号，以及目标 URL 删除代际相同；
- 精确规范化 URL 相同，不使用搜索去重键或有限 URI 删除比较键扩大共享范围；
- 每页有效超时兼容，订阅任务的期限覆盖本次物理请求的原租约；
- 每个订阅者的剩余请求/字节额度至少覆盖付款任务本次获准的上限；
- 任务仍可派发，目标项没有耗尽显式尝试次数。

各自保留独立的任务/项状态、权限代际和租约代数。共享不能增加原付款任务的请求或字节上限，也不能延长物理租约。

### 派发时合并

核心派发某个批读项时，在同一个 SQLite 写事务中寻找已经排队的其他任务，每个任务只取自己的第一个待处理项。所有成员在此事务内捕获同一当前快照和当前全局页面发布序号（`publication_sequence`）；每页有效超时相同。没有兼容订阅者时，原任务仍按单人尝试派发，不必提前创建共享组。

### 派发后的迟到订阅

只在新任务的 `read_many.submit` 创建事务内尝试挂接输入位置 0。相同幂等键的重提返回原任务，不再次加入；不会借这一步抓取其他已存在任务的 pending 项、暂停项或显式重试项。提交事务本身不派发 Worker 请求；未加入的新任务按原调度继续排队。

原尝试必须仍开放加入、租约未过期且尚未结算，并且至少有一个原成员仍有效。除上述共同条件外，还必须满足：

- 新任务此刻的有效超时 `min(per_page_timeout_ms, 剩余任务期限)` 等于原物理 lease 派发时捕获的 `dispatch_timeout_ms`。这个值是派发时的超时上限；`execute_read` 实际开跑时仍可按剩余 deadline 继续收紧，不表示请求在线路上实际使用了同样长的超时。
- 精确 URL 的当前快照 ID 与原捕获一致，当前全局页面发布序号（`publication_sequence`）也与原捕获严格一致。旧的 `@legacy` 捕获不能作为迟到加入证明；当前快照或全局发布水位变化时不加入。该水位不是目标 URL 的专属代数，其他页面的限制变化也会保守拒绝迟到加入。
- 原组累计成员数尚未达到 32。付款任务可以已经取消，只要原组还有其他有效成员；付款归属保持原值。

首次迟到订阅可以在同一事务中把原单人尝试转成两人共享组。新成员记录一次自己的授权尝试，继承原 `attempt_id`、发布捕获和租约截止时间，保留自己的租约代数；不重新获取快照证明，不取得新的物理预算，也不向 Worker 再发一次读取。

候选查询使用精确 URL 和 `read_shared_open_uri` 部分索引。该索引只包含 `running`、仍开放加入且具有正请求预留的付款项，不包含零预留订阅者或已完成历史。每次最多评估查询返回的 32 个候选付款项；这不保证 SQL 总共只扫描 32 行，也不保证遍历所有可能兼容的活动尝试。候选已没有有效成员时，会在同一事务中关闭其加入资格。

## 物理请求与账本

最先取得调度机会的任务是固定付款任务。只有它预留请求和字节预算，向 Worker 发送一个 `attempt_id`。其他成员是订阅者，不再重复预留或计费，也不会凭合并扩大付款任务的出站上限。

schema13 引入的 `read_shared_attempts` 保存物理请求、固定付款任务、原始预留、累计成员总数和已知/未知结算；`read_shared_members` 保存每次尝试的成员关系。`read_job_items` 继续保存每个成员自己的尝试和发布状态，schema15 另外保存派发超时上限与加入关闭状态。显式重试产生新的尝试，不改写此前的共享请求账本。

Worker 返回的已知用量只结算到原付款任务；未知执行保留该任务的整份预留。即使付款任务已经取消，它仍承担此前授权且为其他订阅者继续执行的这一次物理请求。费用不会被转给其他任务，也不会因为取消而被清零。所有成员的结果、收据和结算在同一事务内提交；正文快照只保存一次。

`job.get` 增加 `shared_reads`：成员尝试数、订阅尝试数、待结算/未知尝试数，以及关联的已知请求/字节数。`job.results.items[]` 对共享尝试增加 `shared_read`，包含 `attempt_id`、`payer_job_id`、付款输入位置、成员数、角色和结算状态。

这些 `associated_*` 字段说明一次共享工作与任务的关系，**不得相加当作额外物理用量**。原有 `usage.external_requests/content_bytes`、未知预留与 `budget.charged_*` 仍表示实际归属到本任务的消耗。关联用量未知时返回明确的未知状态，而不是伪报为零请求成功。

## 取消、暂停与发布

`job.control(cancel/pause)` 先推进被操作任务的持久代数并撤销其发布资格。只要同组仍有有效成员，就不发送 `fetch.cancel`；付款任务取消也不会取消其他订阅者。最后一个有效成员离开时，核心才请求 Worker 协作停止。

有效成员检查和关闭加入使用 SQLite `BEGIN IMMEDIATE` 写事务，跨 Store 句柄与迟到加入串行。核心在事务内持久设置 `sharing_closed=1`，提交后才向 Worker 发送协作取消，避免检查后又有人加入已准备停止的尝试。同一 `attempt_id` / 租约代数一旦关闭，不会因时钟回拨重新开放；旧尝试的迟到关闭也不能封闭后续显式重试。

关闭仅禁止新成员加入，不剥夺已有成员原本有效的收据资格，也不提前把预留结算为未知。结果仍由真实回包或原租约到期路径结算；已有成员能否发布仍按原屏障逐一判断。

取消 RPC 不是发布屏障。Worker 可能已经下载完成或迟到返回；提交时仍逐成员重新检查任务状态、权限、期限、租约和删除代际。只有仍有效的成员能得到收据。已取消/暂停的成员不会因为另一个成员成功而取得自己的任务结果，但同 owner 的正常权限仍决定其对其他已保存资料的访问。

主体撤权或 URL 删除会使相关成员全部失去资格。没有有效订阅者时不写正文。共享成员的收据写入失败会回滚整个正文/索引/收据事务，再由失败路径结算一次物理用量。

## 重启、保留与边界

进程重启后成员关系和付款归属不变。持久租约尚未过期只说明账本中的尝试仍待结算，不证明原 Core 或 Worker 进程还活着，也不保证物理请求仍在执行。未过期租约不会重复派发；原执行已丢失而仍无可靠回执时，等待原租约到期后整组标记执行未知，付款任务保留整份预留，订阅者记录关联未知状态。不会自动重发。只有任务原本允许的次数、剩余预算和期限均满足时，才可通过显式 `retry_failed` 发起新的尝试。

任务压缩仍要求原有至少七天的稳定终态资格。压缩一个任务保留永久幂等键和含共享统计的摘要；物理请求记录在其他成员明细仍存在时继续保留，因此付款任务先压缩不会丢失剩余成员的付款归属。最后一个成员明细退休后，已结算组才可回收。活动或未结算成员仍由原有任务/预留条件保护。

## schema15 升级与验证范围

升级前停止旧 Core。schema14 → 15 在事务中为 `read_job_items` 增加 `dispatch_timeout_ms INTEGER NOT NULL DEFAULT 0` 和 `sharing_closed INTEGER NOT NULL DEFAULT 1`，并创建上述部分索引。旧运行项没有可证明的派发超时和开放状态，因此保持 0 / 1，不接受迟到订阅；原租约、成员、预留和完成/结算路径保留，不伪造历史派发信息，也不提前结束旧尝试。新物理 lease 才记录捕获的超时上限并开放加入。旧 Core 打开升级库返回 `E_SCHEMA_VERSION`，不支持新旧进程混用数据库；备份恢复隔离保持。

当前接续的基线反例、正式回归、独立迁移与审核、整合执行分别见[本批验证记录](../validation/shared_read_late_20261024/README.md)，只以实际关闭的执行记录作为结论。本文描述实现合同，不预先声明候选测试或新 CI 成功。

本实现没有新增真实网站批准、凭据共享、跨 owner 复用、恢复隔离豁免或付费回退。后续 direct 与持久通道 / crawl / search 的统一协调、更广取消矩阵、独立撤销 journal 连续性、广泛长时运行和完整 CACHE-01/B-24 验收仍按原计划推进。合成 Worker、可控时钟和 SQLite 双连接用例只覆盖各自场景，不替代真实公网、任意断电或多节点演练。
