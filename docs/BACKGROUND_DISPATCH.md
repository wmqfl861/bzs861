# 后台调度与停止语义

持久任务使用四条固定执行通道。每条通道一次只持有并执行一份租约；没有按任务创建线程，也没有在内存中预先领取一批租约。

| 通道 | 工作 | 并发上限 |
| --- | --- | --- |
| fixture | 离线 fixture 入库 | 1 |
| read | `read_many.submit` 的持久读取 | 1 |
| discovery | `map.submit` 与 `crawl.submit` 的 robots、目录和页面步骤 | 两类合计 1 |
| search | `web.search.start` 的持久来源查询 | 1 |

后台调度启用且只有 fixture 能力时，仅启动第一条通道。配置 Worker 后，后台最多有三个外部 RPC 同时等待，另有一个 fixture 步骤。普通同步 HTTP 请求由 HTTP 入口自己的执行上限控制，不计入上述后台上限。真实 Worker RPC 每次使用独立连接；Python Worker 用独立异步请求处理它们，保留站点、来源、主机的准入和并发限制。

慢读取不会阻止 discovery 或持久来源查询取得下一次派发机会；慢 discovery 和慢来源查询也不会占住其他类别的执行通道。每个类别内部仍按原持久队列轮转；map/crawl 继续共享一个通道，单个类别内部的慢请求仍会推迟同类别的后续工作。同一来源或站点的配额、冷却和并发限制仍可合法推迟请求。本改动不承诺任意请求独立执行或通用吞吐指标。

## 租约、预算和取消

各通道继续调用原有 Store 事务来领取租约、预留预算和提交结果。读取共享组仍在领取物理请求时确定，不把在途的新订阅者加入已有请求；不同 owner 不合并。来源和站点的持久准入没有旁路。

取消、暂停、主体撤权、URL 删除和发布策略仍由原来的持久代际与提交前检查决定。其他通道并行执行不赋予迟到响应新的发布资格。已知用量按原规则结算一次；未知 RPC 失败保留整份预留，不自动重新发送。

## 停止与生命周期

`BackgroundWorker` 是拥有固定线程集合的可移动句柄。调用方必须让 Store、FixtureCatalog 和 WebService 活到句柄停止并完成 join 之后。句柄析构、被移动赋值替换或部分线程启动失败时，都先请求所有已启动通道停止，再逐个 join；没有脱离句柄生命周期的后台线程。线程全部创建成功前由启动闸门阻止领取工作；部分启动失败时先停止，再打开闸门并 join，因此不会在构造失败的清理中等待已发出的 RPC。

停止请求会唤醒空闲通道。已获租约但尚未开始 RPC 的读取、discovery 和来源步骤在检查到停止时按原停止路径处理。已在执行的 RPC 仍受原有有限超时和持久提交栅栏约束，可以在停止后完成当前步骤；停止不会把一次执行未知改写成零用量，也不会立即中断 socket。完成当前步骤后不再进入下一轮领取。跨类别不再保证固定的 read→map→search 交替顺序。

## 验证范围

正式回归在 `tests/fairness.cpp` 和 `tests/e2e_crawl.py`：持有读取、discovery 或搜索响应的闸门，必须观察到其他类别完成以后才放行；同时验证每通道最多一个 RPC、停止后的待处理项、未知用量保留、并行迟到响应的取消栅栏及句柄移动。真实进程测试通过 Core→HTTP RPC→Python Worker→本地合成 HTTP 验证 read/crawl 的双向进展。

测试中的等待上限只用于发现挂起；证据是“其他工作先完成、被阻塞响应随后才放行”的顺序，不是性能服务等级。原跨类别严格交替断言已替换为类别内原有顺序和跨类别进展。来源配置、schema、永久身份、恢复隔离、S2 状态及原工作包签收均保持。
