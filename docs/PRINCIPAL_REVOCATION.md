# 主体撤权

本增量增加一个由 C++ 核心执行的管理操作：`principal.revoke`。它把一个主体永久设为不可使用，适用于已经加载的所有该主体令牌以及以后重新配置的同主体令牌。此操作按主体生效，不是单个令牌的轮换。

## HTTP 与 CLI

```json
{"operation":"principal.revoke","params":{"subject":"alice"}}
```

调用者必须是当前有效的管理员；非管理员返回 `E_FORBIDDEN`，已经撤权的调用者返回 `E_PRINCIPAL_REVOKED`。`params` 只接受一个严格字符串 `subject`，遵循现有主体标识规则，不接受令牌、权限覆盖或调用者身份参数。管理员不能撤销自己的主体。可以预先撤销一个尚未产生数据的主体。

命令行通过相同 HTTP 核心入口执行：

```bash
bzs revoke-principal alice
searchctl revoke-principal alice
```

令牌沿用各自已有的受保护配置或 `SEARCH_API_TOKEN`，不作为命令参数传递。

成功回执包含 `subject`、`revoked=true`、`already_revoked`、`revocation_id`、`revoked_at_ms`、`auth_epoch` 和固定的作用范围。首次撤权把主体的权限代际推进一次。重复调用返回原来的撤权 ID、时间和代际，并将 `already_revoked` 设为 `true`，不会再推进代际、重复计费或重新取消任务。

撤权没有撤销或重新启用入口。删除并重新加入认证文件中的令牌不会解除撤权。持久撤权记录上限为 10,000 条；到达上限时新增撤权返回 `E_QUOTA`，已有记录仍能幂等读取。撤权记录不参与普通任务历史回收。

## 持久行为与在途工作

schema 13 增加 `principal_revocations` 表，保存主体、唯一撤权 ID、时间、管理主体与撤权后的权限代际。记录和主体代际推进、待派发工作取消在同一 SQLite 事务中完成。旧数据库升级不撤权任何已有主体；程序重启和使用另一个 Store 连接后都重新查询该表。

所有 API 调用在开始处理时检查主体状态，并在工作完成、返回结果之前再次检查。存储层同时在读取旧快照、原文证据、分页、会话、任务和接纳新工作时检查。读取 URL 的发布屏障和正文写入也检查主体状态；之前取得的任务租约仍必须匹配原权限代际。因此，等待 Worker 时被撤权的请求不能在回来后发布正文或返回搜索内容。

已有快照、证据和冻结结果不会因撤权被删除。它们不能继续通过被撤权主体的入口获取。其他主体的数据、凭据、会话和任务保持独立。这一行为也防止通过更换同主体令牌重新取得旧数据。

各类任务的结算如下：

| 对象 | 撤权后的行为 |
| --- | --- |
| 排队、暂停的 fixture / 批读 / map / crawl | 待派发项取消，不再取得新租约 |
| 已有 fixture 租约 | 推进租约代际，迟到完成不能写入快照 |
| 已有批读 / map / crawl 网络租约 | 任务进入取消过程，保留原请求和字节预留、尝试身份与期限；收到已知回执后按实际用量结算，否则按原有恢复逻辑保守记为未知 |
| 活动联网搜索会话 | 未派发来源取消，已派发来源记为未知，冻结版本和永久用量回执保留；迟到结果不生成新版本 |
| 本地及已经完成的会话 | 旧权限代际失效，主体状态检查拒绝分页和事件访问 |

撤权不代表能中止已发出的网络请求，也不承诺撤回在撤权之前已经放行到客户端的响应。有限在途 RPC 可以结束，但不能在撤权后通过提交检查。它不触发自动重试、配额重置、未知请求退款或删除幂等键。

## MCP 管理入口

默认 MCP 实例不注册管理工具。需要管理用途时，可明确建立一个 stdio 实例：

```bash
bzs mcp --admin-tools
```

这个实例额外提供 `revoke_principal(subject)`，原始 JSON 类型和未知字段在 SDK 转换前检查；最终身份和权限由 C++ 核心检查。工具标注为会修改状态、有破坏性语义、幂等、无外部网络调用。

`--admin-tools` 与 `--transport streamable-http` 组合被拒绝。当前 HTTP MCP 的客户端会共用后端核心凭据，不能把这个管理能力默认开放给全部客户端。编程方式同时传入 HTTP 鉴权配置和 `admin_tools=True` 也会被拒绝。

## 验证与边界

`tests/revocation.cpp` 覆盖管理权限、严格参数、全部同主体令牌、重启、两个 Store 连接、旧快照和证据、不同主体隔离、各种任务状态、已知及未知用量、迟到结果和备份隔离。`tests/http_revocation.py` 通过真实 HTTP/CLI 验证认证文件中的多个令牌、旧能力访问、重启与令牌轮换。`tests/e2e_revocation.py` 使用真实 Worker/Core 和受控 HTTP 站点，在观测到请求发出后再撤权，然后释放响应，检查直接读取、批读、crawl 不发布且不重发。MCP/CLI 严格映射由 `python/tests/test_principal_revocation_adapters.py` 验证。

这仍不是独立撤销日志、离线 ACL 重放、公共集合 ACL 或安全恢复的完整实现。撤权记录与业务数据位于同一数据库，不能证明独立撤销连续性。既有备份隔离规则保持：所有备份在没有独立连续性证明时，仍以 `E_RESTORE_QUARANTINED` 拒绝作为在线服务启动。原计划的相应完整验收继续保持未签收。
