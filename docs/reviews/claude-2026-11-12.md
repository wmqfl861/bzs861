### CL-02（P1）R-03 让 `site:` 查询在截断时报 `partial=false`

**现象。** 查询带 `site:` 时，R-03（`9f4dd58`）把 SQL 的 `LIMIT` 从 `max_candidates+1` 放大到 `fetch_limit+1`（`min(max_candidates×10, max_candidates+2000)`），再在循环里跳过 host 不匹配的行。如果目标 host 的文档排在放大后的窗口之外，循环会因为 SQL 结果耗尽而正常结束；这时 `candidates` 没有填满，`partial` 也就一直不会被置为 true。结果是"没找到目标，却报告结果完整"。

**证据。**

- `src/store.cpp:1291-1295`：`fetch_limit` 的计算。
- `src/store.cpp:1361`：`rows.bind(bind,fetch_limit+1)`。
- `src/store.cpp:1369-1378`：host 预过滤，跳过不匹配的行，不计数。
- `src/store.cpp:1379`：只有 `candidates.size()==max_candidates` 时才置 `partial=true`。SQL 窗口被截断的情况没有被检测。
- 合同：`docs/API.md:255`（"预算不足时 `partial=true`"）、`docs/SUBSTRING_INDEX.md:9`（"任何候选层未取尽仍返回 `partial=true`"）。
- `max_candidates` 是公开参数，1–2000（`src/service.cpp:284-295`）。
- R-03 提交没有新增任何回归测试（`git show 9f4dd58 -- tests/` 为空）。

**复现**（`site_partial.cpp`，见 repro R1）。1 篇较旧的目标文档在 `target.example`，再加 N 篇排名更高的 `other.example` 文档，查询 `alpha site:target.example`：

| 核心库 | N | max_candidates | 词项路径 | 子串路径（`"alpha"`） |
|---|---:|---:|---|---|
| R-03 之前（`d89c38b`） | 30 | 1 / 2 | 未找到，`partial=true` | 未找到，`partial=true` |
| 当前（`a2e5e4f`） | 8 | 1 | 找到 | 找到 |
| 当前（`a2e5e4f`） | 30 | 1 / 2 | **未找到，`partial=false`** | **未找到，`partial=false`** |

在默认 `max_candidates=2000` 下，需要超过 4,000 篇排名更高的其他 host 文档才会触发。语料较大时（例如有几千篇页面都含常见词 `python`），带 `site:` 的查询就可能触发；调用方显式传入较小的 `max_candidates` 时，门槛会成比例降低。

**影响。** Agent 依赖 `partial` 判断要不要缩小查询或换种问法。报告"完整"却漏掉结果，比如实报告"不完整"更糟。这是 R-03 引入的回退。

**修改方案。** 把 host 条件直接下推到 SQL，删掉放大窗口和循环内的预过滤，恢复原来"多取一行"的 `partial` 判断：

1. 对 `q.hosts` 的每个 host 追加 `AND (d.host=? OR (length(d.host)>length(?) AND substr(d.host,-length(?)-1)='.'||?))`。用 `substr` 而不用 `LIKE`，免得 host 里的 `_` 被当成通配符。多个 `site:` 之间是 AND，与 `matches()` 的合取语义一致（R-02）。
2. 三条候选 SQL（FTS、子串、有界扫描）和 priority 层都要加，绑定顺序要跟着调整。
3. `LIMIT` 恢复为 `max_candidates+1`；`matches()` 照旧做最终判定。
4. 可选：为有界扫描路径加派生索引 `documents(owner,host)`，这不改业务 schema。

如果暂时不想改 SQL，最小修复是统计原始行数：循环结束时如果 `raw_rows==fetch_limit+1` 并且 `candidates.size()<max_candidates`，就置 `partial=true`。但这只能做到诚实披露，召回依然有限，所以推荐下推方案。

**验收。**

### CL-04（P2）MCP 严格参数校验只覆盖部分工具，`map_site` 可能被静默放宽

**现象。** `BzsMCPServer.call_tool` 只对 `_RAW_ARGUMENT_TYPES` 里列出的工具做原始 JSON 类型校验（`python/bzs/mcp_server.py:44-62,74-91`）。代码注释说明了原因：SDK 会把字符串 `"null"` 解析成 None，"会省略显式范围并静默选择更宽的站点默认值"。`crawl_site` 在列表里，但参数几乎相同的 `map_site`（`:344-355`）和 `read_urls`（`:314-324`）都不在。

| 调用 | 结果 |
|---|---|
| `crawl_site(scope_path="null")` | 拒绝：`E_SCHEMA: scope_path must be an absolute URL path` |
| `map_site(scope_path="null")` | **转发给核心，且不带 `scope_path`**，核心使用站点默认的更宽范围 |
| `map_site(max_urls="null")` | 转发，不带 `max_urls`，使用默认值 |
| `read_urls(max_requests="null")` | 转发，不带 `max_requests`，使用默认预算（每个 URL 18 个请求） |
| `read_urls(max_bytes=true)` | 转发为 `max_bytes=1` |
| `map_site(unexpected_field=1)` | 未知字段被静默丢弃 |

**影响。** Agent 明确要求的收窄（范围、预算）被静默丢掉。这些值仍受站点审核范围和核心上限约束，所以不越过安全边界，但会让任务访问第三方站点的范围和次数超出调用方的意图。这正是项目已经为 `crawl_site` 专门修过的那类问题。

**修改方案。**

1. 不再手写 `_RAW_ARGUMENT_TYPES`，改为在 `build_server()` 里遍历已注册的工具，用 `inspect.signature` 和 `typing.get_type_hints` 自动生成类型表，覆盖所有工具：`int` 拒绝 `bool`，`str | None` 拒绝字符串 `"null"`，`list[str]` 逐项检查元素类型，并拒绝未知字段。
2. `scope_path` 的 `^/` 规则同时用于 `crawl_site` 和 `map_site`。
3. 新增参数扫描测试：对 `server.list_tools()` 里的每个工具、每个可选参数，分别发送字符串 `"null"`、错误的 JSON 类型和一个未知字段，都必须得到 `ToolError`；同时检查 `list_tools()` 公布的 schema 里没有 `null` 类型，`additionalProperties=false`。

**验收。** repro R2 里除第一行外全部变成"拒绝"；新扫描测试覆盖 `list_tools()` 返回的全部工具；现有 MCP 端到端测试不回退。

### CL-08（P2）Windows 上的秘密文件没有 ACL 保护，MCP 默认用管理员令牌

**证据。**

- POSIX 下核心会拒绝组或其他人可读的认证文件（`src/service.cpp:18-24`），Windows 下没有任何等价检查。
- Python 端只在非 Windows 上 `chmod`（`python/bzs/config.py:51-52,71-72`）；`os.open(...,0o600)` 的模式参数在 Windows 上会被忽略（`tools/create_auth.py:13`、`probe_state.py:246`）。
- `bzs init` 只生成一个令牌，而且 `"admin": True`（`config.py:76-80`）；MCP 默认读取这个 `api.token`（`mcp_server.py:117-125`）。
- `docs/SECURITY.md` 和 `docs/WINDOWS.md` 都把"Windows 认证文件 ACL"列为未完成。

**影响。** 默认的 `BZS_HOME`（`%USERPROFILE%\.bzs861`）会继承用户目录的 ACL，通常只有本人、SYSTEM 和 Administrators 可读，风险有限。但 `BZS_HOME` 一旦放到 `C:\` 下的其他目录（本地 agent 用过 `C:\bzs861-audit` 这类路径），这些目录默认给 Authenticated Users 读取甚至修改权限，管理员令牌和 worker 令牌就可能被同机的其他账户读取。管理员权限目前只控制 `principal.revoke` 和 `backup.create`（`src/service.cpp:185,371`），MCP 不暴露 `backup.create`，所以这一项定为 P2 而不是 P1。

**修改方案。**

1. Windows 上，`bzs init`、`mcp-token add`、`create_auth.py` 写完秘密文件后设置受保护的 DACL：断开继承，只授予当前用户 SID 完全控制，可选再加 SYSTEM。可以用 ctypes 调 `SetNamedSecurityInfoW`，也可以调 `icacls "<path>" /inheritance:r /grant:r "<当前用户>:F"`。`BZS_HOME` 目录本身同样处理。
2. 新增 `bzs doctor`（或在 `bzs start` 时检查）：如果秘密文件的 ACL 授予 Everyone、Users 或 Authenticated Users 读取权限，就报错。核心的 `Auth` 在 Windows 上可以用 `GetNamedSecurityInfoW` 做同样的检查，或者至少在文档里说明由启动器负责。
3. 最小权限：`bzs init` 生成两个令牌，`owner`（非管理员，供 MCP 使用）和 `admin`（只给 CLI 管理命令用）；旧的单令牌配置继续兼容。

**验收。** Windows CI 的 `windows-python` 加一个真实 ACL 测试：init 之后，用 `icacls` 或 `GetNamedSecurityInfoW` 读到的 DACL 只包含预期的 SID；`doctor` 能检出宽松 ACL；MCP 默认使用非管理员令牌。

### CL-10（P2）测试耗时和 Windows watchdog（issue #4）

**证据与测量。** `CMakeLists.txt` 的 Windows 分支写着：Debug 下 `direct_shared` 260 秒、`sessions` 273 秒，因此 watchdog 提到 420 秒，并把原因归为"每次提交 fsync 加 Debug CPU"。`src/store.cpp:247` 设置 `journal_mode=WAL; synchronous=FULL`。本轮在 Linux（ext4，fsync 真实执行）上实测：

| 套件 | Debug + FULL（现状） | Debug + OFF（实验） | Release + FULL |
|---|---:|---:|---:|
| sessions | 22.2 s | 21.7 s | 10.1 s |
| direct_shared | 20.2 s | 19.5 s | 8.3 s |
| core（`bzs_tests`） | 9.4 s | 7.3 s | 7.7 s |
| long_document_recall | 43.7 s | – | 12.9 s |

所以在这台 Linux 机器上，fsync 不是主要开销，Debug 编译本身才是（Release 快 2.2–3.4 倍）。Windows 上 Debug 比 Linux Debug 慢约 12 倍，更可能的原因是 MSVC Debug 运行库的迭代器检查和 Defender 实时扫描 SQLite 文件。**这个原因本轮无法在 Windows 上验证**，下面给出验证步骤。

**修改方案。**

1. 在 Windows 11 本机上做 2×2×2 的测量：Debug 对比 RelWithDebInfo、`synchronous` FULL 对比 OFF（只在测试里通过环境变量切换，例如 `BZS_TEST_SQLITE_SYNCHRONOUS=OFF`）、测试临时目录是否加入 Defender 排除。把结果写进 issue #4。
2. 核心库没有用 `assert()`（全树为 0），不变量检查都通过会抛异常的 `require()` 完成，所以 RelWithDebInfo 不会丢失任何检查。建议 Windows CI 对重型持久化套件（sessions、direct_shared、capacity_cycles、long_document_recall、cache_freshness_*）改用 RelWithDebInfo 门禁，Debug 只跑快速子集。
3. 测量确认后，Windows watchdog 回到不超过 Linux 的 3 倍；关闭 issue #4，附上数据。

**验收。** issue #4 附带测量表；Windows CI 总时长下降；没有删除任何断言或用例（用例数和断言数与改动前一致）。

### CL-12（P3）`fuse()` 的"供体一致性"与注释不符，结果取决于来源顺序

**证据。** `src/web.cpp:339-342` 的注释说 url、title、snippet 总是来自同一个被选中的命中。但 `:343-349` 的实现是：更优的命中如果 title 或 snippet 为空，就保留组内已有的值。于是较差的命中先到并带有标题时，输出会是"更优命中的 URL + 较差命中的标题和摘要"；顺序反过来就不会这样。

**影响。** 在 R-01 下，同组 URL 只差主机名大小写或默认端口，属于同一个资源，所以语义影响很小，发布检查也会覆盖组内全部贡献 URL。问题在于代码和文档不一致，而且结果依赖来源顺序。

**修改方案。** 二选一并写进注释和 `docs/API.md`：(a) 严格供体，`better` 时无条件整体替换 url、title、snippet；(b) 允许在等价 URL 之间补齐空字段，但与顺序无关（例如先收集组内全部命中，再按 rank 确定性地选取）。

**验收。** 新增测试：同一组输入按所有来源顺序排列，输出完全一致。

### CL-13（P3）本地池把重型查询和 `stats` 放在同一个 2 线程池里

**证据。** `apps/searchd/main.cpp:73-89` 把 `search.once`、`search`、`search.page`、`find`、`document.read/range` 和 `stats`、`job.get`、`capabilities`、`session.get` 一起归入本地池；`:344` 默认 `local_threads=2`。

**影响。** 两个重型本地查询（例如只含 NOT 的查询，上一轮测得单次 0.6–1.1 秒）就能让 `stats`、`job.get` 这类毫秒级调用排队。P1-B 修好了"远程慢调用饿死本地调用"，但本地内部仍会互相挤占。

**修改方案。** 先测量：`--local-threads 2` 下并发发 4 个重型 `search.once` 和 16 个 `stats`，记录 `stats` 的 p95。如果 p95 超过 1 秒，就再拆出一个元数据池（1 个线程，只接 `stats`、`job.get`、`job.results`、`session.get`、`session.events`、`capabilities`、`search.modes`）。

**验收。** 上述场景下 `stats` 的 p95 小于 200 ms。

### CL-14（P3）内部异常不留痕迹

**证据。**

- `apps/searchd/main.cpp:202-204,272-275`：`catch(const std::exception&)` 直接返回 500，不记录异常类型和内容。
- 后台通道 `src/service.cpp:416,421,441,457,469`：任务执行抛异常后会尝试把它记成失败；如果这一步也失败，就整个吞掉，任务只能等租约到期。
- clang-tidy `bugprone-empty-catch` 共报 19 处，要分开看。上面后台通道这一类是真正的"吞错"。其余大多是有意的回退：URL 规范化失败时保留原值（`src/store.cpp:455-471,779,791`，`src/map.cpp:546,628`，`src/web.cpp:822`），或者有注释说明的降级，例如取消时尽力通知 worker、发布围栏不依赖这一步（`src/web.cpp:1025,1782`），以及 `src/web.cpp:1201`、`src/map.cpp:408`。这一类不用改，没有注释的补一行注释即可。

**影响。** 现场出现 `E_INTERNAL`，或者后台任务卡在租约里时，日志里没有任何可用于诊断的信息。

**修改方案。** 加一个 `log_internal(where, exception)`：输出结构化 JSON（事件名、位置、异常类型、`what()` 截断到 200 字节），不包含 URL、查询、正文和令牌。searchd 的两处 `catch(const std::exception&)`、后台通道的 `catch(...)`，以及"连失败状态都写不进去"的内层 catch 都调用它；`stats` 里增加 `internal_errors` 计数。有意回退的 catch 不改行为，没有注释的补一行注释。

**验收。** 新测试注入一个后台异常，stderr 中出现对应事件且不含 URL；`internal_errors` 加 1。

## 5. 优化方案（不是缺陷，但值得做）
