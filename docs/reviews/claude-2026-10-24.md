## 必须修复（P1）

这三项在现有测试里都不会出现，因为测试的文档量和调用次数都很小；按 agent 的真实用量跑一段时间就会碰到。三项都已写程序复现，输出见"实际测试与复现结果"。

### P1-1 永久身份上限：一万次之后永久不能搜索、不能建任务（已复现）

- 机制：每次本地 `search` 都会调用 `local_stream_locked`（`store.cpp:1011`），写一行 `search_stream_receipts`；`web.search.start` 也写一行（`sessions.cpp:203`）。这张表在整个代码库里没有任何 DELETE。容量检查是每 owner 10,000、整个部署 100,000（`sessions.cpp:57`、`140`）。
- 任务同理：`job_capacity_locked` 数的是 `jobs` 全表（`retention.cpp:65-68`，上限 10,000 / 50,000），`jobs` 行永不删除；压缩只归档已结束的 web 任务（`retention.cpp:43`、`115-123`），fixture 任务连归档都不会。
- 复现：第 10,001 次本地搜索返回 `E_SESSION_BACKPRESSURE`（429），把时钟拨过 30 天仍然 429；第 10,001 个任务返回 `E_QUOTA`（429），30 天后 `compact_jobs` 回收 0 个，仍然 429。
- 影响：`API.md:108` 和 `SEARCH_SESSIONS.md:49` 把它写成"有界保留"，但实际后果是一个每天 100 次本地搜索的 agent，约 100 天后这个用户就永久不能再搜；部署级上限由所有用户共用。到顶后没有任何接口能恢复，只能手工改库。
- 建议：幂等身份只在固定窗口内有效（常见做法是 24 小时到 30 天），窗口外连同摘要一起删除；没有幂等键的本地 `search` 不写永久身份；到上限时回收最旧的过期身份，而不是拒绝新请求。如果一定要长期记账，记到按天聚合的计数表。

### P1-2 本地搜索每小时最多 64 次（已复现）

- 机制：`Store::search` 每次都建持久会话，存活 1 小时（`store.cpp:986`），每 owner 同时最多 64 个（`store.cpp:926`），部署最多 256 个（`sessions.cpp:56`）。MCP 的 `search_local` 每次都调 `search`，但只取第一页、从不翻页（`mcp_server.py:409-418`）。
- 复现：每秒一次本地搜索，第 65 次被拒，`E_QUOTA`"Too many active search sessions; wait for expiry"（429）。
- 影响：MCP 适配层用同一个核心令牌访问 searchd（`mcp_server.py:113-121`），所以多个 agent 合计每小时 64 次；被拒后要等最早的会话过期，最长一小时。每次搜索还把全部命中行冻结入库，却没人翻页。
- 建议：给 `search_local` 一个不建会话的一次性查询（或只在调用方要翻页时才冻结）；会话满了就回收最旧的，而不是拒绝新的。这一项修好后，P1-1 的搜索部分也就不再被本地搜索触发。

### P1-3 本地索引过 2,000 篇后，短语、符号和非拉丁词查不到旧文档（已复现）

- 机制：`fts()` 只为"纯 ASCII 单词"和"纯 CJK"两种叶子生成 FTS5 候选（`query.cpp:287`）。带引号短语、含 `+#:./\` 的词（`c++`、`node.js`、`example.com`）、url 字段、含非 ASCII 非 CJK 字符的词（`café`、`Москва`、德语变音）、CJK 与 ASCII 混写的词（`iPhone手机`），都走"按创建时间倒序扫最新 `max_candidates` 篇"（`store.cpp:937-942`，默认 2,000，`service.cpp:274`），更早的文档不看，只把 `partial` 置为 true。
- 复现：入库 2,101 篇，答案在最旧的一篇。`machine learning` 走 FTS，命中 1 篇；`"machine learning"`、`c++`、`node.js`、`café`、`Москва` 全部走 `bounded_scan_recent`，命中 0 篇。
- 影响：每次 `read_url` 和 crawl 都会入库，2,000 篇很快就到；MCP 工具描述里还把 `"exact phrase"` 列为可用语法（`mcp_server.py:404-405`），返回里只有一个 `partial` 字段，没有说明哪些文档没看。同一个扫描还是下一节 P2-5 里的慢点。
- 建议：短语改为按词边界匹配（和常见搜索引擎一致），就能直接用 FTS5 的 phrase 查询；分词器把其他 Unicode 字母数字也当作词（并做大小写折叠）；`c++`/`c#` 在分词器里已经有共位词元（`tokenizer.cpp:70-83`），查询侧却把它们归为 literal 不用（`query.cpp:135`），接上即可；其余符号字面量可以拆成词元短语做候选，再精确复核。修改前需要重建索引，`fts_tokenizer_version` 已经为此留了接口。

## 蓝图优化建议

蓝图本身结构严谨：83 个工作包、161 项验收、10 个切片，`plan_v1_2.py check` 本机通过。问题在执行顺序和成本：S1 卡在一个只有你能做的来源决策上，开发转而深挖 S2，而流程证据的增长远快于产品。现在状态是 37 包部分实现、46 包未开始、0 包签收，S0/S1/S2 都未完成。

### 1. S1 卡住的根因：来源决策没人做

- S1 完成标准第 1 条要求至少 2 个经有效审核、显式启用并经 S0 实测可用的来源，含 1 个通用网页源；S0 的定义是"在你的机器上实测"。这两步都要你亲自做，云端的开发 agent 做不了。
- `config/sources.json` 的 17 个来源全部 `enabled:false`、审核状态都是 candidate。其中 6 个是 Bing、DuckDuckGo、百度、Mojeek、搜狗、360 的结果页抓取，商业搜索引擎的条款一般不允许自动抓取，按项目自己要求的 `automated_access=approved` 很难批准，"通用网页源"这一格因此一直填不上。
- 交接文档给下一位 agent 的指示是"先修当前精确提交上任何真实失败，再按原蓝图扩展剩余 S2 工作"（`NEXT_AGENT.md:25`），没有任何一步指向来源决策。
- 建议：在清单里已有适配器的 API 来源中挑选，例如 `marginalia`（分类是通用网页）加 `wikipedia_zh`/`wikipedia_en`，先由你按 ADR-0003 现查它们当前的条款和配额，审核通过后启用，再在你的机器上跑一次 S0 探测。S1 闭环前冻结 S2 新功能。

### 2. 顺序：先让一个真实 agent 任务跑通，再加固

S2 已经做了发布代际、主体撤权、共享读取、条件重验证、会话版本等很深的加固，而 P1 和 P2-1~P2-4 这类问题只有在真实使用里才会暴露。建议下一批只做四件事：修 P1；两个来源上线；在你机器上让 agent 跑通"搜索→读页→本地检索→引用证据"；再根据这次使用里发现的问题决定 S2 还剩哪些必做项。

### 4. 流程与证据成本

交接规则要求每次增量"按源文件与二进制哈希记录作者、独立、升级和最终执行，保留原失败"（`NEXT_AGENT.md:33`），结果是 validation 目录现有 1,351 个文件、占仓库文件的 86%，大量是构建日志、ctest 日志和冻结的执行输入清单。建议：日志和冻结清单放到 CI artifact，不进 git；每个增量只更新一份状态页（做了什么、测了什么、还差什么）；独立复核只用于 P1 级改动。

### 5. 文档形态

交接文档压得很密，一句话常常一两百字、夹着大量提交号和 CI 编号（例如 `NEXT_AGENT.md:21` 一段讲 Windows watchdog 的话）。人读不动，agent 也容易只抓住字面规则。建议拆成三份：目标规格（稳定）、状态矩阵（每个切片一行）、变更日志；每份开头先用 5 行写清楚"现在能用什么、不能用什么"。

## 建议的下一批顺序与需要你拍板的事项

下一批建议只做"修 P1 + 让 S1 真正闭环"，改动集中在会话与任务的容量逻辑、查询与分词、缓存和来源配置。

1. 修 P1-2 和 P1-1：`search_local` 改为不建会话；幂等身份和任务键加保留窗口并回收；补"一万次之后仍能搜索、建任务"的回归测试（可直接改写附录里的 `permanent_caps.cpp`）。
2. 修 P1-3：短语按词边界匹配、分词器支持 Unicode 字母、`c++`/`c#` 查询侧接上，升 `fts_tokenizer_version` 重建索引。
3. 修 P2-1 到 P2-4（Vary、重定向缓存、robots 的 User-agent、字符集），都是小改动，直接影响真实网页。
4. 来源上线（需要你）：选定 2–3 个来源并完成审核记录，在你的机器上跑 S0 探测，然后启用。
5. 端到端验收：在你的机器上通过 MCP 让 agent 完成 3–5 个真实任务（例如"查一个技术问题、读两三个页面、引用原文作答"），记录失败点，作为 S1 签收依据。
6. 之后再定 S2：只保留第 5 步里暴露出的必做项；P2-6、P2-7 的并发问题在多个 agent 同时使用之前修掉。
