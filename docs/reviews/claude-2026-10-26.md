## 4. 本轮问题、修改方案与验收

### P1-A 长文档上的短语、符号查询仍漏旧文档（P1-3 遗留）

**现象。** 不能走词级 FTS 的查询——带引号的短语、`c++`/`node.js` 这类符号字面量、`café`/`Москва` 这类非 CJK 的非 ASCII 词、`url:` 字段——走子串候选路径：每个叶子取最多 8 个三元组做 AND 过滤，结果按 `created_at DESC` 截到 `max_candidates`（≤2,000），再逐篇精确复核。文档短时过滤很有选择性；真实网页动辄几十 KB，常见英文词的三元组几乎每篇都有，过滤放过的文档远超 2,000，最旧的真匹配被时间截断挡在外面。

**证据。**
- `src/store.cpp:1205-1210`：子串路径 `ORDER BY s.created_at DESC,d.id LIMIT ?`；`1251-1253`：取满 `max_candidates` 即置 `partial=true` 并停止。
- `src/query.cpp:214-216`：引号短语保持"原始子串"语义，不检查词边界；`289-317`：短语、字面量、非 CJK 的非 ASCII 词不生成 FTS 候选；`319-365`：子串 gram 表达式。
- `src/tokenizer.cpp:193-217`、`include/bzs/tokenizer.hpp:22`：查询侧每个叶子最多取 8 个 gram。

**复现**（long_doc_recall；英文语料切成 4,000 篇 × 30 KB，唯一含 "machine learning" 的文档最旧）：

| 查询 | 检索路径 | gram 过滤放过 | 找到目标 | partial | 耗时 |
|---|---|---:|---|---|---:|
| `machine learning` | fts5_bm25_verified | – | 是 | false | 44 ms |
| `"machine learning"` | fts5_substring_verified | 2,505 | **否** | true | 249 ms |

**影响。** Agent 很常用引号短语和代码符号。语料里一旦有足够多的长页面，这些查询就退化成"只查最近 2,000 篇"。和上轮 P1-3 是同一类故障，只是门槛从"2,000 篇文档"变成"2,000 篇被 gram 放过的文档"。`partial=true` 是诚实的，但 agent 拿不到目标。

**修改方案**（二选一；语义由用户在第 7 节 D7 决定）：

- **方案 A：不改语义，两层候选（先做这个）。**
  1. 对含 ASCII 单词部分的短语/字面量叶子，额外生成 FTS5 词级候选：短语 `"machine learning"` → FTS5 短语查询；字面量 `node.js` → 短语 `"node js"`；`c++` → `"c++"`（分词器已经为 `c++`、`c#` 输出同位 token，`src/tokenizer.cpp:87-100`）。这一层按 bm25 排序，取前 `max_candidates`。
  2. 剩余预算再用现有 gram 候选按时间补足，以保留"词内子串"的命中（例如 `"achine learn"`）。
  3. 两层去重后照旧精确复核；第二层被截断时仍报 `partial=true`。排序：第一层命中按 bm25，第二层命中按现有 `match_score` 排在其后（或统一用 `match_score`，二选一并写进文档）。

  候选只是生成器，正确性仍由精确复核保证，所以不改变已发布的语义；而词对齐的出现（绝大多数真实命中）不再受文档年龄影响。
- **方案 B：改语义（作为蓝图修改，见 B-4）。** 把引号短语定义为"词序列匹配"，这是主流搜索引擎的做法。短语直接走 FTS5 短语查询 + bm25，不需要时间截断；gram 索引只服务符号字面量、未分词的文字和 `url:` 字段。实现最简单，但要改规格和"一词短语匹配更长单词"这类现有用例。

**验收。**
1. 新增原生测试：≥4,000 篇、每篇 ≥30 KB 的自然语言文本（用仓库内 ≤1 MB 的语料确定性切片，不访问网络），最旧一篇含目标；`"machine learning"`、`node.js`、`café` 三类查询都必须返回该文档。
2. 上轮 P1-3 的短文档回归保持通过；方案 A 下词内子串用例也保持。
3. 记录 Release 下该查询的耗时（只记录，不设 SLA）。

### P1-B 请求执行没有等待队列，MCP 不重试

**现象。** `searchd` 的 `RequestExecutor` 只接纳 `request_threads` 个请求（默认 `min(--threads, 32)`，即 8），满了立即返回 503 `E_REQUEST_BACKPRESSURE`，不排队。`web.read` 在整个抓取期间占着一个请求线程（超时默认 20 秒、最长 60 秒）。MCP 这一侧，`CoreClient` 收到 503 不重试，`_call` 直接抛 `ToolError`。

**证据。**
- `apps/searchd/main.cpp:66-110`：`submit()` 在 `admitted_>=capacity_` 时返回 false，注释写明"There is no additional waiting queue"；`274-278`：返回 503；`342`、`424`：默认 8 线程；`src/web.cpp:896`：读取超时 1–60 秒。
- `python/bzs/core_client.py:38-47`：没有重试；`python/bzs/mcp_server.py:128-135`：`CoreError` 转 `ToolError`。

**复现**（backpressure.py：回环 `searchd --no-worker`，先导入 400 篇 × 60 KB；"慢调用"是一个只含 NOT 的 `search.once`，单次几十到几百毫秒，比一次真实网页读取快得多）：

| 场景 | `--threads 8`（默认） | `--threads 2` |
|---|---|---|
| 同时发 24 个慢调用 | 8 个成功，16 个 503 | 2 个成功，22 个 503 |
| 同时发 24 个 `stats` | 24 个成功 | 23 个成功，1 个 503 |
| 线程被慢调用占满时，再发 16 个 `stats` | **16 个全部 503** | **16 个全部 503** |

**影响。** Agent 框架普遍并行发工具调用，一次 5–10 个 `read_url` / `search_local` 很常见。现在只要并发超过线程数就会随机硬失败；慢读取占满线程时，连 `stats`、`get_job` 这种毫秒级调用也会失败。上轮 P2-7 是"慢"，现在是"随机失败"，对 agent 更糟。

**修改方案。**
1. `RequestExecutor` 加有界等待队列：深度默认 `4 × request_threads`（新增 `--request-queue`），每个请求最长排队默认 30 秒；只有队列满或排队超时才 503，错误里带 `retry_after_ms`。取消控制槽保持独立，不变。
2. 把出网的慢操作（`web.read`、`web.search`、`web.search.start` 等）和本地操作（`search.once`、`document.range`、`find`、`stats`、`job.get`、`session.*`）分到两个池，或至少给本地操作保留 2 个线程，避免慢抓取饿死本地查询。
3. `CoreClient` 对 `E_REQUEST_BACKPRESSURE` 做有界退避重试（例如最多 3 次、带抖动、总时长 ≤10 秒）。`main.cpp:66-68` 的注释已保证被拒的请求没进入 Service、没预留任何工作，所以对任何操作重试都安全。其他 503（如 `E_STORAGE_BUSY`）按操作是否幂等决定。

**验收。**
1. 回环测试：`--threads 2`，Worker 桩每次读取延迟 2 秒，同时发 16 个 `web.read` 和 16 个 `stats`：0 个失败；有保留线程时 `stats` 的 p95 < 1 秒。
2. 队列满时 503 带 `retry_after_ms`；`CoreClient` 单测覆盖"重试后成功"和"重试耗尽后报错"两种情况。
3. 真实 MCP stdio 测试：并行 24 个 `search_local` 全部成功。

### P2-A 永久身份数据无限增长，且不计配额

**现象。** P1-1 的修法是把"可回收明细"和"永久身份"分开：容量只数未归档的任务，身份行永远保留。

- 每次冻结本地搜索写一行永久收据：`src/store.cpp:1383` → `src/sessions.cpp:134-144`；每个联网搜索会话也写一行（`sessions.cpp:203`）。代码里没有任何地方删除 `search_stream_receipts`。
- 任务压缩后保留 `jobs` 行和最多 8 KiB 的 `archive_json`（`src/retention.cpp:12`、`135-139`），永不删除。
- owner 配额只数快照字节（`src/store.cpp:797`、`826`、`1534-1536`）。

**复现**（identity_growth）：12,000 次冻结搜索和 12,000 个任务全部成功（P1-1 确实修了）；之后库里留下 12,000 行收据、12,000 行任务（11,500 行已归档），归档 JSON 共 4,991,000 字节（本例 fixture 任务每行约 430 字节，读取/爬取类任务更大，上限 8 KiB）；owner 的 `content_bytes` 显示为 0。

**影响。** 单用户长期运行时，这些行只增不减：每次冻结搜索、每个联网会话一行，每个任务一行加最多 8 KiB。量不算大，但没有上限、不计配额、不能清理，和"存储可控"的目标矛盾，也拖慢相关索引。这是"永久幂等身份保留"这项决定的直接代价。

**修改方案。**
- 需要用户决定（第 7 节 D5）：推荐把身份保留期限化。终态后保留 90 天（可配置），之后删除收据和任务行；过期的幂等键重放返回 410 `E_IDEMPOTENCY_EXPIRED`，API 文档写明"同一幂等键只在保留期内有效"。
- 不论 D5 怎么定，下面三点都应该做：
  1. 没有幂等键的本地冻结搜索不写永久收据，会话过期时连收据一起删掉（过期后返回 404 而不是 410，差别很小）。
  2. 归档摘要的字节计入 `stats`，并计入 owner 存储配额。
  3. 打开 `auto_vacuum=INCREMENTAL`，压缩后执行 `incremental_vacuum`，否则删了也不还磁盘。

**验收。** 可控时钟测试：超过保留期后相关行清零、重放返回 410；`stats` 显示归档字节；无键冻结搜索过期后 `search_stream_receipts` 不再增长。

### P2-B 子串 gram 索引：写放大大、不计配额、大的中文页面会溢出

**现象。** `indexed_grams` 对标题、正文、URL 的每个码点生成一元、二元、三元 gram（每字段最多 65,536 个不同 gram，每个 token 最长 19 字节），写入 `substring_fts`。

**证据。** `src/tokenizer.cpp:157-192`；`src/store.cpp:717-722`（写入）；配额只数快照字节（见 P2-A）。

**测量**（Release；300 篇，每篇 50 KB，共 14.3 MiB 正文；同一程序分别链接 `44253a7` 和 `6410d27` 的核心库）：

| 语料 | 磁盘 `44253a7` → `6410d27` | 磁盘 / 正文 | 写入耗时（每篇） |
|---|---|---|---|
| 中文 | 62.8 → 165.2 MiB（×2.63） | 4.39 → 11.55 倍 | 13.1 → 40.8 ms（×3.1） |
| 英文 | 50.0 → 76.7 MiB（×1.53） | 3.50 → 5.36 倍 | 6.7 → 14.5 ms（×2.2） |

另外按同样规则统计不同 gram 的数量：英文 977 KiB 只有 25,260 个，不会溢出；中文 191 KiB 已有 58,952 个，以这份语料推算，大约 220 KiB 以上的中文页面就会超过 65,536，整页只记一个 `boverflow`。溢出页对任何子串查询都是候选，中文大页面一多，P1-A 的时间截断会在这些页面上重现。

**修改方案。**
1. **CJK 段不建 gram。** CJK 字符在 `content_fts` 里本来就逐字有位置，纯 CJK 叶子已经走 FTS（`src/query.cpp:314`）。索引侧跳过任何含 CJK 码点的 gram 窗口；查询侧只从不含 CJK 的窗口选 gram，纯 CJK 叶子不再生成 gram 约束；中英混合叶子（如 `Python教程`）对 CJK 段追加 FTS 短语约束，对非 CJK 段用 gram 约束。候选仍是精确匹配的超集。在这份中英混排的中文语料上，每篇 50 KB 的不同 gram 数降到原来的约 20%（见附件 R4），纯中文文本降得更多，溢出问题也随之消失。这是派生索引的变化，不需要升级业务 schema。
2. gram 索引的字节计入 `stats`，并计入 owner 存储配额（或单独设上限）。
3. 如果采纳 P1-A 方案 B 和 O-2（Unicode 分词），gram 索引还能进一步收缩到"只覆盖含符号的窗口和未分词的文字"。

**验收。** 用同样的测量：中文 300 × 50 KB 的磁盘 ≤ `44253a7` 的 1.4 倍、写入耗时 ≤ 1.5 倍；英文不比现在差；P1-3、P1-A 回归全部通过；新增中英混合、CJK + 符号、溢出边界用例。

### P2-C robots：常见写法仍导致整站 deny_all

**现象。** 上轮 P2-3 修完后，无关组里的 `Googlebot/2.1`、`Baiduspider+` 已被正确忽略，但下面这些写法仍让整站 deny_all：
- `User-agent: 008`（80legs 爬虫的 robots token，常见于站点的屏蔽列表，见 [knownagents.com/agents/008](https://knownagents.com/agents/008)）——去掉非字母后为空；
- `User-agent: Mediapartners-Google*`——含 `*`；
- 非 ASCII 的 UA，例如 `Яндекс`。

**证据。** `python/bzs/worker/robots.py:98-103`、`161-163`。复现 robots_residual.py：这三种都是 `deny_all / robots_invalid_product_token`，其余为 `rules`。

**修改方案。** 采用 RFC 9309 解析器（例如 Google 开源的 robotstxt）的做法：只取 UA 值开头的 `[A-Za-z_-]+` 作为 token，大小写不敏感；token 等于 `bzsbot`、或值恰好是 `*`，才算匹配本爬虫；其余（空 token、非 ASCII、带 `*` 的其他产品名）一律视为无关组忽略。只对"看起来指向 BzsBot 但格式损坏"的值（如 `BzsBot*`、`Bzs Bot`）保持保守拒绝。

**验收。** 上面三例返回 `rules`，diagnostics 含 `ignored_unrelated_product_tokens`；现有"自身/通配损坏即拒绝"的用例保持。

### P2-D 后台四条 lane 各自串行

**现象。** 后台按类别分成 fixture、read、map/crawl、search 四个线程，但每个线程一次只做一步，做完无条件再等 20 毫秒（即使队列里还有活）。

**证据。** `src/service.cpp:381-389`（`background_lane`：每步之后固定 `wait_for` 20 ms）、`421-462`（每类一个线程）。

**影响。** 一个慢读取（最长约 60 秒）挡住所有其他 read_many 任务；一个慢站点的 map/crawl 挡住所有其他站点；一个联网搜索会话的多个来源逐个执行，其他会话排队。这和 agent "同时研究几个问题"的用法冲突。

**修改方案。** 每条 lane 改成小线程池（建议 read 4、map/crawl 2–4、search 4，可配置），同一站点的礼貌间隔继续由 Store 里已有的按 origin 冷却和配额保证；一步有活就立刻取下一步，空闲时才等待。Store 的 lease 都在事务和 Store 锁里完成，并发 lease 本身是安全的，但要补测试。

**验收。** Worker 桩每次抓取延迟 2 秒：4 个不同 origin 的 read_many 任务总耗时约等于 1 个任务，而不是 4 倍；同一 origin 的任务仍遵守 `min_interval_ms`；现有崩溃恢复测试保持通过。

### P3（低优先级，放进后续批次即可）

- **P3-A FTS 路径复核全部候选。** 候选已按 bm25 排好序，FTS 路径也不再重排（`src/store.cpp:1282` 只对非 FTS 路径排序），但即使 `limit=10`，`1259-1281` 也会把最多 2,000 篇正文逐篇拷出来复核。测量（2,000 篇 × 30 KB 英文，`search.once`，`limit=10`）：`the`（几乎每篇都有）复核 2,000 篇、338 ms；`light`（245 篇含有）复核 245 篇、62 ms。提前终止后，前者只需复核约 11 篇。做法见 O-1。
- **P3-B 共享读取与取消的复杂度。** `DirectReadFlight/Member`、1,024 个句柄、120 秒期限、固定取消控制槽，加上 durable 共享和迟到加入——单用户、0 个已启用来源的阶段用不上。不要求删，但不要再扩展（见 B-2）。
- **P3-C 墙钟超时。** `6410d27` 仍在诊断 Windows `direct_shared` 的 90 秒超时；本轮在 2 vCPU 上跑 ASan，`sessions` 和 `direct_shared` 也都在重型用例中途撞到超时。重型套件标为 slow、默认门禁跑快速子集，比逐平台逐次调超时更稳。
- 上轮 P3-1（伪装 UA）、P3-2（json-c 全局锁）、P3-6（证据部署级上限）未改，仍然成立。

## 5. 优化方案

**O-1 本地检索**
1. FTS 路径提前终止：复核到 `limit + 1` 个命中即可停止，并据此设置 `partial`。最后一步的发布可见性过滤可能还会剔除命中，所以要留余量或循环补足。冻结会话（`limit` 最大 500）同样适用。
2. P1-A 方案 A 第一层的 bm25 分数也用作子串路径的排序依据（现在子串路径按出现次数打分）。
3. 只有 NOT 的查询仍是"最近 2,000 篇有界扫描"，在 API 文档和 MCP 工具描述里写明；或者要求至少一个正向条件。

**O-2 Unicode 分词（同时修正蓝图与实现的不一致）**
蓝图第 3 节写的是"自研 FTS5 分词器：包装 unicode61，中日韩字符输出单字并叠加二元组"，实际的 `bzs-ascii-cjk/2` 只认 ASCII 单词和 CJK 字符，其余码点直接跳过（`src/tokenizer.cpp:104-106`）：`café` 只剩 `caf`，`Москва`、`Ελλάδα` 完全不进 FTS，只能靠 gram 索引。按 Unicode 字母/数字切词（unicode61 规则 + NFKC + casefold，CJK 仍逐字）之后，这些词直接走 FTS 和 bm25，gram 索引的负担也随之减轻。这属于 INDEX-01 的范围，需要重建一次派生索引，不需要升级业务 schema。

**O-3 并发与吞吐**
1. P1-B 的排队与分池，P2-D 的 lane 线程池。
2. json-c 全局锁（上轮 P3-2）：请求线程从 IO 线程分离后，所有 JSON 构造、拷贝、析构都在争同一把锁。先加一个"8 线程并发 `search.once`"的吞吐测试量化，再决定用 `ENABLE_THREADING` 构建 json-c，还是跨线程只传深拷贝后去掉全局锁。

**O-4 存储**
P2-A 的保留期与 incremental vacuum；P2-B 的配额计入；`stats` 按项输出（快照、正文 FTS、gram 索引、会话与收据、任务归档、证据），让用户看清空间花在哪里。

**O-5 冻结复杂度，不再扩展**
跳转缓存证明链、来源冷却证明与旧数据修复、URI 删除别名、durable/direct 共享读取与成员取消，都已实现且有测试。建议：保持现状，不再扩展；1.0 之前不新增同类"证明链"机制。以后如果维护成本高，再考虑简化，例如跳转缓存只缓存"同站 http→https、补斜杠"这类确定性跳转。

**O-6 验证材料与交接文档**
1. 每批的原始日志、二进制哈希清单、逐用例输出放到 CI artifacts 或 GitHub Release 附件；仓库里每批只留一份 ≤20 KB 的 README 和一份 ≤20 KB 的 result.json（命令、输入哈希、通过/失败计数、artifact 链接）。
2. `docs/handoff/NEXT_AGENT.md` 只保留"当前步骤"，历史移到 CHANGELOG。现在的文件把四五批历史叠在一起，每段都写"以上文为准"，下一位 agent 很难判断哪条还有效。
3. 仓库现有的 48 MB validation 要不要从 git 历史中移除，属于用户决定（D3）。用户决定之前，不要改写历史。
