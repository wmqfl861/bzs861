# HTTP 请求执行与背压

`searchd` 将传输 IO 与业务执行分开。接收请求、Host/Origin/认证和 Content-Type 检查、`GET /healthz`、响应写入留在 IO 线程；进入 `Service::dispatch` 的普通业务调用交给固定数量的请求线程。本批另设固定 **1 个取消控制执行槽**，用于符合下述严格分类的 `web.read.cancel`。慢 Worker RPC 只占用所属执行槽，IO 不执行 Service 或等待 Worker；取消可以在普通业务池已满、控制槽仍有余量时被接纳。

这项隔离不改变权限、来源审核、预算、幂等、持久任务或 Worker 的准入规则。Store 的 SQL、正文复制和最终发布投影仍可能短暂持锁；本地搜索具体边界见[搜索并发](LOCAL_SEARCH_CONCURRENCY.md)。它不是任意负载下的吞吐或健康检查时延保证。

## 2026-10-26 P1-B：有界排队与本地保留池

普通池仍由 `--request-threads` 控制，新增 `--request-queue 0..256`，默认
`4 * request_threads` 个等待名额；`--request-queue-timeout-ms 1..30000` 默认30秒。
另外保留 `--local-threads 1..32`（默认2）给小型、严格解析的本地请求。
本地池默认等待深度为 `max(4 * request_threads,16)`；显式指定 `--request-queue`
则两个业务池都采用该深度（包括0）。`ready` 报告两池线程数/队列深度和排队期限。
本地请求包括 `search.once`/冻结搜索与分页、`document.read/range`、`find`、
`stats`、`job.get/results`、`session.get/events/cancel`、capabilities和search.modes；
超过4096字节、格式不合或未知操作回普通池。分类不是业务授权，Service仍重读原正文。

固定取消控制池仍是1槽、0额外排队，4096字节严格资格和原权限规则保持。
三个池不能互借容量；普通/本地队列满或待开始调用到期时返回503，错误项带
`retry_after_ms=1000`。到期任务由独立期限线程从队列原子移除，即使所有执行线程
仍被占用，也会返回拒绝；该任务之后绝不进入Service。已开始的业务不受排队期限取消。
`CoreClient.call/call_sync`只对503 + `E_REQUEST_BACKPRESSURE`再提交，最多3次，
在最初调用后的10秒窗口内带抖动退避；原请求字节不变，总调用期限不重置。
已接纳任务继续使用原业务期限，因此不承诺整个读取10秒内完成。
其他503、传输断连和未知执行结果不自动重试。显式零队列的旧回归继续保留。

## 历史配置与容量

| 配置或限制 | 当前合同 |
| --- | --- |
| `--threads` | IO 线程数，1–64，默认 8。 |
| `--request-threads` | 普通业务执行线程数，1–32；省略时取 `min(threads,32)`，不包含取消控制线程。 |
| `control_threads` | 固定为 1，无新增可调 CLI 参数；只用于符合分类条件的 `web.read.cancel`。 |
| `control_body_limit_bytes` | 固定为 4096；只有不超过该字节数的完整正文才进行控制通道分类。 |
| 接纳数 | 每个执行池分别限制“执行中 + 已接纳但尚未开始”的总数；普通池最多等于 `request_threads`，控制池最多为 1，均无额外等待额度。 |
| 活动连接 | 既有上限 64；超出时关闭新连接，不承诺返回 JSON 背压信封。 |
| 请求尺寸 | 正文最多 2 MiB，header 最多 8 KiB。 |
| socket 期限 | 请求读取与响应写入各 5 秒；写入期限在准备响应时重新设置。 |

例如 `--threads 2 --request-threads 4` 使用两条 IO 线程、四条普通业务线程及一条取消控制线程。启动的 `ready` JSON 报告 `threads`、`request_threads`、`control_threads=1` 和 `control_body_limit_bytes=4096`，`--help` 也说明固定控制配置。CLI 参数在启动时严格检查范围；没有 HTTP 请求可以临时扩大线程数或取得额外等待额度。

内部可以短暂保存已接纳但尚未被线程取走的调用，不过每个池的“执行中 + 待开始”始终受自己的容量约束，不另设溢出队列。**普通池和控制池不能互借容量。** 符合控制分类的取消只提交给控制池；即使普通池有空槽，控制池满时也返回 HTTP **503**，错误码 **`E_REQUEST_BACKPRESSURE`**。普通请求不会因控制池空闲而扩大接纳量。拒绝发生在进入 Service、创建业务身份、预留业务预算或派发 Worker 之前；传输检查失败仍优先返回相应 Host、Origin、认证、路由或 Content-Type 错误。

背压拒绝本身没有发起业务操作。后续显式提交仍须遵守原权限、预算和幂等合同；服务端不会因这一错误自动重试。容量不足也不会通过启用新来源、扩大抓取范围或切换身份来绕过。

## 取消控制通道的严格分类

分类位于既有 Host、Origin、路由、Bearer 认证和 Content-Type 检查之后。只有不超过 **4096 字节**的正文才用原 `Json::parse` 完整解析，并须同时满足：

- 顶层对象只含 `operation` 与 `params`，`operation` 是字符串 `web.read.cancel`。
- `params` 是对象且只含 `read_id`；该值是 48 位小写十六进制字符串。
- 原 JSON 检查全部通过，包括重复键、UTF-8、嵌套及尾随数据检查；不能靠正文中出现操作名的字符串片段进入控制池。

大小超限、重复键、未知字段、缺失字段、错误类型或无效 ID 均回到普通池选择。普通池有容量时，原 Service 路径解析并返回原错误或执行结果；普通池已满时，仍可先返回原 503 背压。**4096 字节是控制分类上限，不是新的 API 正文上限**：例如添加大量合法空白的取消正文超过该值后，只能按普通请求接纳；既有 2 MiB 总正文限制保持。

分类不访问 Store 或 Worker，也不判定句柄是否存在、属于当前 owner 或已经完成。接纳之后仍由 `Service::dispatch` 重新解析原正文并执行主体有效性、owner、句柄状态和撤权检查。此通道不包括 `web.read.prepare`、`job.control`、`session.cancel` 或其他操作，不改变它们的接纳和权限合同。

固定槽隔离的是普通业务池饱和这一条件。控制槽本身被占用、64 个活动连接已满、IO 无法调度或 Service 等待 Store 锁时，仍不能承诺接纳或即时完成。共享读取的取消确认、付款归属及协作停止边界见[成员取消合同](DIRECT_READ_CANCELLATION.md)；新增槽不构成取消 SLA。

## 健康检查和超时

`GET /healthz` 不占业务执行槽，也不访问 Store 或 Worker。它仍经过 Host/Origin 检查，并与其他请求共用 IO、监听器和活动连接上限。业务线程全部被占用时，健康检查仍可由 IO 处理；连接已满或 IO 无法调度时，没有单独的健康检查保留通道。

`ready=true` 表示这个传输入口可以响应，不能据此推断来源可用、业务槽空闲、后台任务完成或完整产品已通过验收。测试中观察到的响应先后关系不构成健康检查 SLA。

5 秒是各次 socket 读写操作的期限，不是所有业务请求的整体期限。操作进入业务线程后，继续使用其原有的 Worker 超时、持久/单调期限和预算。业务完成后的响应写入另外受 5 秒限制；不以传输期限延长业务授权。

## 断连、取消和停止

客户端断连时，已接纳的业务可能已经开始或完成。此改动不把断连转换为业务取消，也不自动重新派发请求；响应未送达不能证明没有执行。持久任务继续使用 `job.control` 或原会话取消接口，迟到响应仍须通过租约、owner、撤权、删除和发布栅栏。未知结果按原规则保留预留和幂等身份。

停止时，普通和控制两个执行器均停止接纳，并清除各自尚未开始的已接纳调用；已执行的同步调用继续在原有期限与提交检查下结束。正常退出时主程序先 join 控制线程，再 join 普通请求线程，二者都早于 Service、Store、Worker 和响应所依赖的 IO 对象销毁。停止后不保证还能向客户端交付结果，不能据此推导应当自动重试。

两个池的线程分别由执行器拥有，没有分离线程；构造任一线程池中途失败时，停止并 join 该池已创建的线程，再传播异常。两个执行器均在 IO 对象之后声明，异常展开时也先停止并 join 线程，再销毁 IO 与 Service。此生命周期说明覆盖这两个执行池，不是对操作系统线程资源耗尽的产品验收承诺。

## 与后台调度的关系

普通 HTTP 请求线程数与固定取消控制线程分别限制各自的同步 API 调用。已提交的持久任务另由 [四条固定后台通道](BACKGROUND_DISPATCH.md) 执行：fixture、read_many、map/crawl、持久来源搜索。后台上限不消耗这两个请求池的槽，也不能将各个上限相加后当作所有外部 HTTP 请求的总并发数；单次业务内部的来源扇出、站点/主机并发及共享预算仍按各自合同执行。

固定通道只隔离不同类别。map/crawl 继续共享一条通道，同一类别内部的慢工作仍可能推迟后续工作；来源或站点配额也可合法延迟派发。健康检查、请求池或后台通道的存在都不授予来源/站点启用资格。
