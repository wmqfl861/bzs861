# 批量读取与抓取的持久公平调度

本增量补充 JOB-01 / FT-005、BATCH-01 / FT-026、MAP-01 / FT-027、CRAWL-01 / FT-028 的有限单机调度行为，并回归 ROBOTS-01 / FT-081、C-02、C-15 相关限制。原 83 个工作包、161 个验收映射和 10 个切片保持不变；这些用例不构成整个工作包的签收。

## 执行次序

`web.read_many` 使用一个持久队列；`web.map` 和 `web.crawl` 共用另一个持久队列。每次成功接纳新任务时，核心在写入任务的同一 SQLite 事务中分配递增的队列序号。每次成功预留一次执行租约时，任务获得新的序号并排到该类别队尾。序号独立于墙钟时间和随机任务 ID。

因此，同一毫秒提交的任务仍按实际提交事务次序排列。一个 20 页读取任务每获得一次执行机会后，其他已就绪任务可以轮到；后来持续提交的任务也不能不断以默认零序号插到已有抓取前沿之前。重复提交同一个幂等键不会重新排队、增加派发次数或额外请求网络。

保证以**该类别成功预留的、满足执行条件的租约机会**为单位。若某任务前面有 N 个符合条件的任务，它获得下一次机会之前，这些前面的任务各至多先取得一次租约；新任务加入队尾。暂停、站点冷却、并发上限、robots、预算、截止时间、删除或权限变更仍可使任务暂时不符合执行条件。这不承诺固定秒数内完成网络请求，也不保证受同一站点限制的任务能够同时运行。

阶段三保留 fixture/import、批量读取、map/crawl 每类一次机会的原后台循环；此前没有发现这些类别之间的饥饿问题。阶段五集成后，联网来源会话也获得一次独立循环机会，并在自己的持久队列内逐来源轮转。来源请求和 HTTP 超时仍各自有界，见 [SEARCH_SESSIONS](SEARCH_SESSIONS.md)。

## 重启、升级与控制

队列序号和预算、租约在同一事务内持久化。重启沿用已有次序，不把任务全部重新放到队首。未知执行结果仍保留其完整预留计费，不能借重新排序退款或重做失去回执的 HTTP 步骤。

升级前的读取任务没有保存实际提交事务序号，首次迁移保留确定性的旧 `created_at/id` 次序，直到每个旧任务取得一次执行机会；不能声称恢复了旧版本从未记录的真实同刻提交顺序。旧 map/crawl 已保存的派发序号和计数器继续使用。新接纳任务统一使用递增票号。调度计数器不能随[过期详情回收](JOB_RETENTION.md)删除、重算或归零。

暂停任务保留原有票号，恢复后按该票号参与选择。取消、过期、删除或预算不足的项目按原合同终结或跳过；没有成功预留 HTTP 租约就不消耗一个调度回合。任务和结果继续按 owner 隔离，队列公平性不扩展读取权限。

## 验证范围

新增 `bzs_fairness_tests` / CTest `fairness` 用例覆盖：

- 相同时间的严格提交顺序、多个读取任务逐项轮转，以及短任务在长任务未完成时取得机会。
- 持久队列重启、未知租约保留全额预留、两个 Store 连接取得不同租约。
- 暂停、恢复、取消、过期、站点冷却和另一 origin 的继续执行。
- 持续新 map 任务进入时旧前沿仍前进；map/crawl 共用队列与现有任务间规则一致。
- 实际后台线程中批量读取与 map 两个类别都前进。
- 日历停止原因在交错调度和重启后保留；不同文章路径、重复 query 键次序、版本号和有限数字 ID 不被误停。

这些原生用例使用显式 Fake Worker，无真实 HTTP。两个 Store 连接的租约用例按顺序调用连接；它不是同时启动多个进程的吞吐测量。重启与未知租约用例也不替代真实进程崩溃、任意断电或文件系统损坏实验。CI 中应执行 `fairness`，并将新增可执行文件纳入现有 sanitizer 和 Windows 原生测试门槛。

trap 仍是已固定版本的有限启发式规则；此阶段加强交错运行和负例证据，没有声称识别所有互联网陷阱。B-39 的完整分布式调度、BACKUP-00 的独立撤销日志恢复，以及真实目标环境的性能门槛继续按原计划推进。
