# 本机启动器生命周期

`bzs start` 和 MCP 自动启动现在必须完成就绪与健康检查；失败不再以成功返回，MCP 自动启动失败也不会继续启动一个误导性的服务。各组件首行就绪等待由 `config.json` 的 `startup_timeout_s` 控制，默认30秒、允许1..120秒；它不改变任何业务请求时限。首次冷启动实测曾超过新引入的10秒试验值，该失败被保留，最终改为显式可配置的冷启动预算。首行最多4096字节，要求正确事件、版本、回环地址、组件和端口。历史日志中的旧就绪行不算本次启动成功。

stdout/stderr 写入本机私有日志文件，而非未持续消费的 PIPE。即使父启动器退出，后续日志也不会填满管道阻塞服务。就绪首行后的大量日志不计入首行长度。日志目前不自动轮转，仍需部署运维处理容量。

同一 BZS_HOME 的启动/停止操作使用排它文件锁。持久记录仍位于 `run/worker.pid`、`run/searchd.pid`，但内容改为私有 JSON：格式版本、组件、PID、进程出生身份、端口、starting/ready 状态。Linux 使用 boot_id + /proc starttime，持久停止使用 pidfd；Windows 使用准确的 ctypes HANDLE 类型、进程创建 FILETIME 和同一进程句柄终止/等待。不会向0、1、负数、越界值或身份不匹配的进程发信号。

启动失败只回收本次创建且尚未失去句柄的子进程；先终止、等待，再按需杀死并等待。已经运行的已有 Worker 不会因新 Core 启动失败而被清理。停止未确认退出时保留记录并报错，不声称停止成功。Windows 延续原来的终止进程方式，不宣称等同 POSIX SIGTERM 的优雅退出。

Windows 的 venv `python.exe` 是启动器残根，真正的解释器是它的子进程；只终止记录的 PID 会把真实 Worker 留在后台继续占用端口。清理与持久停止因此以出生身份已验证的根进程为锚，用一次进程表快照收集父链可达的全部后代并从深到浅终止；快照之外或身份不符的进程绝不发信号。根进程已退出后到达的清理无法再定位其树，保持只处理仍可验证的根（与 PID 文件保守语义一致）。

旧版仅存数字的 PID 文件不能建立安全身份，自动控制会拒绝。升级前应先用原环境正常停服；若遗留旧记录，由操作者核对确无相关活进程后移走，不能只凭 PID 数字自动接管/删除。Linux 无 pidfd、非 Linux/POSIX 其他平台、权限不够或记录损坏均保守拒绝。本轮不承诺 macOS 支持、PID 恶意伪造防御、崩溃瞬间零遗留进程或完整进程监督器。

数据库离线维护与启动器相互独立：维护必须取得数据库排它锁，不以“PID 文件不存在”作为停服证明。业务 schema15 和网络政策不变。
