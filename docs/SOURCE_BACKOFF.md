# 搜索来源退避上限

搜索来源的 `Retry-After` 和 API `backoff` 每次最多形成 **24 小时**的新限流等待。秒数和 HTTP-date 在正常范围内按原值保留；配置的 `cooldown_rate_ms` 与该等待取较大值。超过上限的值不会变成数十年的持久冷却，也不会改变来源的配置启用、审核或发布状态。

这个上限仅适用于搜索来源。通用 HTTP `Retry-After` 解析、自动站点/robots 的等待与拒绝规则保持原有合同。遇限流仍返回 `rate_limited`，本次搜索为 partial；不会立即重试、切换身份或自动启用来源。

## 对外诊断

同步 `web.search` 的来源结果，对 `rate_limited` 增加以下兼容字段。持久搜索执行复用同一退避策略，内部保存完整来源结果；本次不新增会话诊断接口。

| 字段 | 含义 |
| --- | --- |
| `retry_after_ms` | 经过 0–86400000 毫秒边界约束的上游要求；缺失、负数或非整数旧 Worker 字段按 0 处理 |
| `cooldown_ms` | 本次配置冷却与有界上游等待的较大值；不是当前共享预算剩余等待的替代值 |
| `retry_after_clamped` | 上游值超长，或 Worker 已报告截断；无论旧 Worker 是否提供此字段，Core 都独立检查数值 |
| `retry_after_limit_ms` | 发生截断时为 86400000 |

截断事件的 `error` 和 `web.sources` 的 `state.last_error` 以 `E_RETRY_AFTER_CLAMPED:` 标识。后续响应仍按原逻辑更新最后状态/错误；这些字段不是永久事件日志。`state.cooldown_remaining_ms` 继续报告当前持久共享预算的真实剩余等待。

Worker 在释放共享来源并发槽之前安装同样有界的冷却栅栏。已排队的同服务适配器在期限前不能开始新请求。Source manifest 的三个 `cooldown_*_ms` 字段在 Worker 和 Core 均要求整数 0–86400000，布尔值不视为整数。

S0 Probe 对截断也记录 `retry_after_clamped` / `retry_after_limit_ms`。限流后本次 probe 仍停止该共享服务预算；即使冷却已到期，resume 也不会重新执行已停止、已完成或结果未知的工作。

## 既有冷却与旧数据库

现有失败退避取最大绝对期限，晚到成功不能取消冷却。原 `parse_error` 的配置退避仍为 `cooldown_error_ms × 3`，最大 72 小时；在途的后续 429 或成功不会把这个合法期限缩短成 24 小时。每次新报告按报告当时的 Core 时钟计算期限；系统时钟回拨后，合法绝对期限的剩余时间可能超过 24 或 72 小时，此时保留原期限。

Core 在现有 `settings` 中按共享来源预算保存 `source_cooldown_proof/<id>` 辅助记录，仅累计**已经过边界检查的新报告**所形成的最大绝对期限。未知旧记录因 SQL `MAX` 留下的更大值不会被当成新证明。证明与报告在同一事务内提交，晚到成功不清除它；双句柄、状态读取和重启后仍保护该合法期限。该退避修正最初沿用 schema13，没有新增表结构；当前业务格式已由独立的 [URI 删除身份迁移](URI_DELETION_IDENTITY.md) 升为 schema14，退避证明规则保持。

旧 schema 没有每次响应的时间，最后状态也可能被晚到响应覆盖。请求时间不能替代响应时间，`剩余 > 72 小时` 无法证明旧记录非法。因此，无证明历史记录采用**保守的一年极端异常启发式**，仅在以下条件同时成立时自动修复：

- 现有期限不受已保存的合法证明覆盖。
- 现有期限同时超过“当前时间 + 365 天”和“最近已知事件时间 + 365 天”。最近事件取最后请求时间、最后成功时间的较大值。
- 最近事件时间不在当前时间之后；遇到这种无法解释的回拨或未来时间状态，保留旧期限。

满足上述条件的旧记录，以最近有效事件为固定锚点：最后状态为 `rate_limited` 时加 24 小时，其他状态加 72 小时，同时不低于任何已证明合法期限。没有有效旧事件时间时，仅首次修复使用当前时刻。该启发式能恢复正常时钟下真实旧代码产生的约 31 年等待；它不能从不完整旧列还原所有历史，也不声称能识别全部非法期限。**不足一年或事件时间存在歧义的旧值可能继续保留**。

修复在 `source_admit`、`source_report` 或 `web.sources` 读取调度状态时，以事务写回固定期限，并以 `E_SOURCE_COOLDOWN_CLAMPED:` 标记最后错误。`state.cooldown_last_repair` 持久保留最近一次修复的原期限、修复后期限、固定锚点、观察时间和原因；后续成功不会清掉这项追溯信息。它是最近一次修复记录，并非完整事件日志。

重复查询、重启或其他 owner 查看状态不会滑动续期。旧请求已经足够久远时，修复期限可能已经过去，来源下一次请求仍须通过原启用/审核、最小间隔和日配额检查。来源身份、调用计数、配额、幂等数据和 schema 版本保持。时间加法/剩余时间计算采用有界或饱和运算，避免异常 Worker 值溢出后清掉等待。

本轮只证明离线正式回归中的边界与状态机行为，不代表已启用或实测任何真实来源。
