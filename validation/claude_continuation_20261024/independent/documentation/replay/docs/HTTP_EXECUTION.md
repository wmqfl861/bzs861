# HTTP 请求执行与背压

`searchd` 将传输 IO 与业务执行分开。接收请求、Host/Origin/认证和 Content-Type 检查、`GET /healthz`、响应写入留在 IO 线程；进入 `Service::dispatch` 的业务调用交给固定数量的请求线程。慢 Worker RPC 因此只占用自己的业务执行槽，其他业务在有余量时可以继续，IO 不随同步业务调用一起等待。

这项隔离不改变权限、来源审核、预算、幂等、持久任务或 Worker 的准入规则。Store 的 SQL、正文复制和最终发布投影仍可能短暂持锁；本地搜索具体边界见[搜索并发](LOCAL_SEARCH_CONCURRENCY.md)。它不是任意负载下的吞吐或健康检查时延保证。

## 配置与容量

| 配置或限制 | 当前合同 |
| --- | --- |
| `--threads` | IO 线程数，1–64，默认 8。 |
| `--request-threads` | 业务执行线程数，1–32；省略时取 `min(threads,32)`。 |
| 业务接纳数 | 最多等于业务线程数，包括已执行和已接纳但尚未开始的请求；没有额外的业务等待额度。 |
| 活动连接 | 既有上限 64；超出时关闭新连接，不承诺返回 JSON 背压信封。 |
| 请求尺寸 | 正文最多 2 MiB，header 最多 8 KiB。 |
| socket 期限 | 请求读取与响应写入各 5 秒；写入期限在准备响应时重新设置。 |

例如 `--threads 2 --request-threads 4` 使用两条 IO 线程和四条业务线程。启动的 `ready` JSON 分别报告 `threads` 与 `request_threads`。CLI 参数在启动时严格检查范围；没有 HTTP 请求可以临时扩大线程数或取得额外等待额度。

内部可以短暂保存已接纳但尚未被线程取走的调用，不过“执行中 + 待开始”的总数始终受同一容量约束，不另设溢出队列。容量满时，在进入 Service、创建业务身份、预留业务预算或派发 Worker 前返回 HTTP **503**，错误码 **`E_REQUEST_BACKPRESSURE`**。传输检查失败仍优先返回相应 Host、Origin、认证、路由或 Content-Type 错误。

背压拒绝本身没有发起业务操作。后续显式提交仍须遵守原权限、预算和幂等合同；服务端不会因这一错误自动重试。容量不足也不会通过启用新来源、扩大抓取范围或切换身份来绕过。

## 健康检查和超时

`GET /healthz` 不占业务执行槽，也不访问 Store 或 Worker。它仍经过 Host/Origin 检查，并与其他请求共用 IO、监听器和活动连接上限。业务线程全部被占用时，健康检查仍可由 IO 处理；连接已满或 IO 无法调度时，没有单独的健康检查保留通道。

`ready=true` 表示这个传输入口可以响应，不能据此推断来源可用、业务槽空闲、后台任务完成或完整产品已通过验收。测试中观察到的响应先后关系不构成健康检查 SLA。

5 秒是各次 socket 读写操作的期限，不是所有业务请求的整体期限。操作进入业务线程后，继续使用其原有的 Worker 超时、持久/单调期限和预算。业务完成后的响应写入另外受 5 秒限制；不以传输期限延长业务授权。

## 断连、取消和停止

客户端断连时，已接纳的业务可能已经开始或完成。此改动不把断连转换为业务取消，也不自动重新派发请求；响应未送达不能证明没有执行。持久任务继续使用 `job.control` 或原会话取消接口，迟到响应仍须通过租约、owner、撤权、删除和发布栅栏。未知结果按原规则保留预留和幂等身份。

停止时，请求执行器先停止接纳，并清除尚未开始的已接纳调用；已执行的同步调用继续在原有期限与提交检查下结束。主程序在销毁 Service、Store 和 Worker 之前 join 请求线程，响应所依赖的 IO 对象也活到请求线程退出之后。停止后不保证还能向客户端交付结果，不能据此推导应当自动重试。

请求线程由执行器拥有，没有分离线程；构造请求线程池中途失败时，停止并 join 已创建的请求线程再传播异常。此生命周期说明仅覆盖该请求池，不是对操作系统线程资源耗尽的产品验收承诺。

## 与后台调度的关系

HTTP 请求线程数控制同步 API 调用。已提交的持久任务另由 [四条固定后台通道](BACKGROUND_DISPATCH.md) 执行：fixture、read_many、map/crawl、持久来源搜索。后台上限不消耗请求池的槽，也不能将两个上限相加后当作所有外部 HTTP 请求的总并发数；单次业务内部的来源扇出、站点/主机并发及共享预算仍按各自合同执行。

固定通道只隔离不同类别。map/crawl 继续共享一条通道，同一类别内部的慢工作仍可能推迟后续工作；来源或站点配额也可合法延迟派发。健康检查、请求池或后台通道的存在都不授予来源/站点启用资格。

## 验证与证据

正式回归位于 `tests/integration.py`：用受控 Worker 闸门保留业务响应，检查 `/healthz` 能先返回、额外业务得到 503、拒绝请求未进入 Worker、容量回收和参数边界。独立探针另覆盖默认 8 槽饱和、断连后的单次执行与在途停止；作者、独立与 sanitizer 输入分开记录。有限等待只用于发现挂起，核心证据是闸门释放前的确定顺序和调用次数。

旧 `59081e1` 基线的失败、作者聚焦执行、独立审核、sanitizer 及最终整合结果均见[本批验证记录](../validation/claude_continuation_20261024/README.md)，并绑定准确源码和二进制。本文不预填后续执行次数、未来远端 SHA 或 CI 成绩。本批不改变 64 连接上限、原 socket 期限、schema、来源启用、备份隔离或工作包签收状态。
